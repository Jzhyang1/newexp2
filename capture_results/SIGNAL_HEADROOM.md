# Headroom of non-host signals for prefetching

Question: the `learned` prefetcher (see `DECISIONS.md`, 2026-11-07) uses only what `nbd_server` sees. Its ceiling with
local information is about 80% (FAISS ~85%) because the first request of every FAISS list visit and of every new
Thesios stream cannot be predicted from earlier host requests. How much would signals from *outside* the host stream
buy, and which of them could a real system supply?

Method: **tell the policy the signal as an oracle, then ask what a realistic source of it recovers.** Every oracle
is a prediction file (`{request idx, page, prob=1}`) that `psim` prefetches in union with `learned`
(`--policy "learned+file:path=...,theta=50" --evict lru_seg`); hit and traffic are measured exactly as in
`tools/pf/README.md`. Nothing here is trained; the signal is simply handed over. Generated by
`tools/pf/signal_oracle.py` (FAISS) and `tools/pf/signal_oracle_th.py` (Thesios); files in `logs/pf_signals/`
(gitignored). Metrics: `full_hit` = reads served entirely from cache; traffic = backend pages / no-prefetch demand pages.

Streams: FAISS = the traced 20k-query capture `logs/capture/base` (the only run that has the guest trace, 22.5k host
requests); Thesios = `th_m1g` (150k application reads, 170k host requests). One run each, so differences of a point or
less are noise.

## 1. FAISS: the application's probe list

At the start of each query FAISS has already computed which 8 inverted lists it will read
(`index.quantizer.search`); the traced workload writes them to `trace_marker` (`APP q_begin lists=...`). 93% of host
requests fall inside a query window.

| signal given to the policy | full hit | page hit | traffic | pf used |
|---|---|---|---|---|
| none (`learned` alone) | 74.2% | 75.4% | 1.67x | 50% |
| next probe list only (the one after the list being read) | 77.1% | 81.3% | 1.92x | 46% |
| all not-yet-visited probe lists of the running query | 80.1% | 86.8% | 2.38x | 38% |
| **all probe lists + exact guest residency (oracle: only lists that will reach the host)** | **80.1%** | 86.4% | **1.69x** | 55% |
| probe lists minus lists the *host* saw requested in the last 300 / 1000 / 3000 host requests | 80.1 / 80.1 / 80.3% | 86.8 / 86.8 / 87.0% | 2.37 / 2.32 / 2.16x | 38-42% |
| **all probe lists + guest residency reconstructed from traced page-cache events** (skip a list if >= 50% / >= 80% of its pages are resident at query start) | **80.1% / 80.4%** | 86.8 / 87.0% | **1.68x** | 56% |

Reading it:

* The probe list is worth about **+6 points of hit rate** (74 -> 80), +11 points of page hit.
* Alone it is not affordable: 40% more traffic, because the guest already holds many of those lists and never asks
  for them (used drops to 38%).
* **Guest cache residency is the missing half.** The *exact* answer (which lists the guest will miss on) recovers the
  whole gain at `learned`'s own traffic, and so does a residency map **reconstructed from the guest's real
  `mm_filemap_add_to_page_cache` / `delete_from_page_cache` events** (AUC 0.915 for "this probed list reaches the
  host"). This is the signal RESULTS.md finding 5 found "does not help" for *which list comes next*; combined with
  the probe list it does the opposite, because the two answer different questions (what will be read / will the guest
  need the host for it).
* A host-visible proxy for residency ("I saw it requested recently, so the guest has it") is almost useless
  (traffic 2.38 -> 2.16x at best): lists leave the guest cache in ways the host cannot see.

## 2. Thesios: the application's upcoming reads

Thesios's missing 20-25% are new streams: a read at a place no recent request points to. An application that knows what
it will read next (a compaction job reading a list of files, anything that calls `posix_fadvise(WILLNEED)`) can say so.
Each host request is mapped back to the application read that caused it (99.9% mapped; hashed file placement as in
`kvm/guest/trace/thesios_ondisk.py`), and the oracle lists the page ranges of the *next K application reads*.

| signal given to the policy | full hit | page hit | traffic |
|---|---|---|---|
| none (`learned` alone) | 73.5% | 81.0% | 1.81x |
| next 1 application read | 84.2% | 89.1% | 1.91x |
| next 4 reads | **94.8%** | 96.4% | 2.16x |
| next 16 reads | 98.6% | 98.8% | 3.12x |
| next 64 reads | 96.0% | 96.4% | 8.0x |
| next 4 reads, only 50% of reads carry a hint | 90.7% | 93.5% | 2.03x |
| next 4 reads, only 25% of reads carry a hint | 85.3% | 89.6% | 1.94x |

* This is far larger than anything host-side: **one read of lookahead is +10.7 points, four is +21 points**, at
  +5% / +19% traffic. Even a quarter of reads hinted gives +12 points.
* Past ~16 reads the gain reverses (the pages are fetched long before use and evicted: 8x traffic at 64).
* It requires the application to tell someone. In this repo the application is a trace replayer, so the "hint" is
  free here; for a real workload the cost is an agent in the guest (or a library hook) and a channel to the host.
* File **size / end-of-file** (clip each stream's prefetch at the file's extent, `psim --clip`) is a minor signal:
  -15% traffic, but -1.7 points of hit at the same theta; at equal hit the gain is about +1 point and -3% traffic.
  Most of the Thesios waste ("futile" 45%) is therefore not prefetching past the end of a file.

## 3a. Which signal predicts "this probed list reaches the host"? (conditional sweep, FAISS)

`tools/pf/signal_sweep.py`: for every (query, probed list) a gradient-boosted model predicts whether the list produces host
requests, from groups of signals; "alone" = that group only, "dAUC" = AUC lost when the group is removed from the model that
has all the others (the conditional value). Later 35% of queries held out; 160k (query, list) rows, base rate 2.9%.

| signal group | alone: AUC | added to all others: dAUC |
|---|---|---|
| **popularity** (times the list was probed so far; queries since last probe) | **0.929** | **+0.093** |
| guest residency (reconstructed from page-cache events) | 0.815 | +0.004 |
| host recency (time since the host last saw this list) | 0.585 | +0.028 |
| previous query duration | 0.664 | +0.009 |
| list size | 0.600 | -0.002 |
| probe order (position in the query) | 0.503 | -0.001 |
| guest memory level (`Cached`) | 0.480 | -0.010 |
| all | 0.972 | |

Popularity subsumes residency: hot Zipf-topic lists are the ones the guest keeps, and probe counts come from the application
hint alone, with **no guest tracing**. (The 0.815 here vs 0.915 in section 1 is a different label: section 1 asks "does any host
request fall in the list's page range during the query", this one requires the request inside the query window per list.)
Recency measured in queries is useless (below).

Policy-level check (oracle prefetch of the probe lists that pass the filter, + `learned`, same stream as section 1):

| filter on the probe lists | full hit | page hit | traffic |
|---|---|---|---|
| none | 80.1% | 86.8% | 2.38x |
| skip lists probed in the last 50 / 200 / 800 queries (LRU model of the guest) | 80.1 / 80.1 / 80.3% | 86.8 / 86.8 / 86.9% | 2.36 / 2.35 / 2.26x |
| skip lists probed >= 24 / 12 / 6 / 3 times so far | 80.1 / 80.0 / 79.3 / 78.4% | 86.8 / 86.5 / 85.5 / 84.0% | 2.23 / 2.13 / 1.97 / 1.81x |
| residency reconstructed from guest page-cache events (section 1) | 80.4% | 87.0% | 1.68x |
| `learned` alone | 74.2% | 75.4% | 1.67x |

So an application that only reports its probe lists, with a per-list probe counter, gets +4 points at +8% traffic (>= 3);
adding real residency gets +6 points at +0%. Query-count recency is not a stand-in for guest LRU (the guest's reuse is by
topic popularity, not by recent use).

## 3. What this says about which signals to build first

| signal | where it comes from | measured value | cost |
|---|---|---|---|
| application probe list / upcoming reads (SIGNALS #50 app marker, #29 fadvise) | app hook or library | **+6 (FAISS) to +11..21 (Thesios) hit points** | an application-aware channel; hints can be partial |
| probe counts per list (derived from the app hint) | app hint | popularity filter: +4 points at +8% traffic with no guest tracing | none beyond the hint |
| guest page-cache residency per object (#30, #31, #32) | guest tracing (`filemap` events) or `mincore` on the mmap | makes the FAISS probe-list gain free of extra traffic (2.38x -> 1.68x) | guest tracing perturbs the guest (3x requests at 64 MB buffers, +16% at 2 MB; RESULTS.md caveats); `mincore` untested |
| host-visible "recently requested" residency proxy | host | ~nothing | free |
| file size / EOF (#27) | guest `i_size` | ~+1 point / -3% traffic on Thesios | small |
| per-request host features, readahead state, guest rq flags | host + guest | ~0 (RESULTS.md finding 5, and the offline GBM probe) | n/a |

## 4. Caveats

* Oracles are upper bounds: probability 1, zero latency, no hint noise except where stated. The residency
  reconstruction is the only *realistic* signal measured so far, and it used the full ftrace tracer (which changes the
  workload; here the stream is the traced one, so the policy is evaluated on exactly the stream the signal came from).
* FAISS numbers come from one 20k-query trace; the probe signal is available at `q_begin` (all 8 lists at once), so
  the oracle's timing is realistic, but prefetches are instant in `psim`.
* The Thesios mapping window (1 MiB around each application read) can attribute a host request to a neighbouring
  read; with 99.9% mapped and the monotone-pointer rule the error is believed small but was not measured.
* The conditional sweep (3a) covers only the FAISS list-reaches-host question and the signals already in the joined capture
  (no cgroup/ioprio/HW counters). The Thesios side has no guest trace, so only the application-read oracles were run.
* Nothing here is wired into a policy yet: next step is an `on_hint` channel so `nextreq`/`neighborhood` can use hints as features.

## 5. Reproduce

```bash
tools/pf/build.sh                                   # bin/psim
./bin/python tools/pf/signal_oracle.py              # FAISS oracles  -> logs/pf_signals/*.bin, trace.csv

S=logs/pf_signals
```

# Part 2: hints as a real channel, degradation, and a learned traffic filter

Following the plan "hit rate first, traffic is a separate filtering problem", the oracle files of part 1 were replaced by a
real mechanism: `CachePolicy::on_hint(first_page, npages, aux)`, a hint-consuming policy (`hint`, `policies/policy_hint.cpp`)
and, for the live runs, an in-band hint channel.

## 6. Hint-consuming policy with a learned filter (offline, `psim --hints`)

`hint` fetches a hinted range only if a count table learned online says ranges *like it* reached the host. Features:
popularity (times this range was hinted), the guest's own residency annotation `aux` (from `mincore`, quartiles), size,
and whether the host saw the range requested recently. Label: a host request touches the range within 256 requests.
No oracle data: hints are one per probed list, delivered at query start, exactly what the guest shim sends.

FAISS (20k-query traced run), always in union with `learned`, `lru_seg`:

| configuration | full hit | traffic (pages) |
|---|---|---|
| `learned` alone | 74.2% | 65.8K |
| hints, **no filter** (fetch every hinted list) | 83.0% | 93.5K |
| hints + learned filter, no residency annotation, theta 20 / 30 / 40 | 80.7 / 80.2 / 79.7% | 70.8 / 68.5 / 67.6K |
| **hints + learned filter + `aux` (mincore residency)**, theta 20..50 | **83.1%** | **67.0K** (all thetas) |

* Fetching every hinted list gives +8.8 points but +42% traffic. The filter with only popularity/recency/size features
  keeps 70% of that gain (+6.5 points) for +4% traffic.
* With the guest's `mincore` residency annotation the filter is essentially perfect: **the whole +8.9 points at
  `learned`'s own traffic** (traffic is insensitive to theta because the annotation is nearly deterministic). This is
  better than the part-1 oracle (80.1%) because hints arrive before the query's first request and cover its first list too.

## 7. Degrading the hints (how fragile is the gain?)

`tools/pf/degrade_hints.py` applies channel latency (delay in host requests), noise (a fraction of hint groups point at the
right-sized range in the wrong place) and loss (only a fraction of groups exist) to the oracle prediction files of part 1
(`learned+file:...`; no filter; FAISS = exact-residency probe oracle, Thesios = next 4 reads).

| degradation | FAISS hit / traffic | Thesios hit / traffic |
|---|---|---|
| none | 80.1% / 66.4K | 94.8% / 2066K |
| delay 1 / 3 / 10 requests | 79.0 / 77.4 / 74.8% (same traffic) | 94.4 / 93.0 / 87.8% |
| 25% wrong-place hints | 79.7% / 86.6K | 92.7% / 2857K |
| 50% wrong-place hints | 79.0% / 105.7K | 89.5% / 3581K |
| only 50% of hints delivered | 78.9% / 66.3K | 90.7% / 1939K |

* **Hit rate is robust, traffic is not.** Half the hints wrong costs 1 (FAISS) to 5 (Thesios) points of hit but adds
  60-70% traffic: wrong hints are pure waste. That is the case for the filter, and the reason traffic was split out.
* **Latency matters more than noise for hits**: ten requests of delay costs 5-7 points (the hint must beat the first
  request of its range; FAISS hints come ~1 ms ahead of the first list read).

Caveat: in this part the delay unit is host requests, not time; the live channel below has real latency.

## 8. The in-band hint channel

* **Wire format.** `nbd_server` gets a second NBD port (`hint_port: N` in the config; `run_capture.py --hints on|aux`
  adds it as a third virtio disk, `/dev/vdc`, size 2^50). A hint is a 512-byte O_DIRECT read at byte offset
  `512 * payload`, `payload = (page4k << 8) | (lenclass << 4) | aux`; the reply is zeros. `HintReader` (`disk/nbd.cpp`)
  decodes it and calls `SimReadClass::hint` -> `policy->on_hint`, and the pages the policy proposes are admitted at once.
  In-band, so no vsock/virtio-serial is needed and hints interleave with data reads in the same order the app issued them.
* **Guest shim** `kvm/guest/trace/hints.py`: `Hinter` (sends hints) and `Mincore` (fraction of a file range resident in the
  guest page cache, via `mincore(2)` on a shared mapping of the same file faiss mmaps; no tracing needed).
  FAISS: after `quantizer.search`, before the query reads anything: one hint per probed list (device byte range
  precomputed from the extent map; a real agent would get it from `FIEMAP`). Thesios: when read n is issued, hint read n+K.
* A hint costs the app one extra NBD round trip (~tens of microseconds); the live runs use the simulated-latency mode, so
  guest timings are not meaningful for that cost (see Caveats).

## 9. Live VM results with the hint channel

Real QEMU guests, the in-band channel of section 8, `lru_seg`, nbd_server's own hit ratio and reads-fully-cached
(`logs/pf_live/h_*`; `tools/pf/live_hints.sh`, aux runs re-run after fixing a `mincore` zero-length bug). Traffic = pages admitted
to the cache (`cache.csv`) relative to the no-prefetch run of the same workload (FAISS 34.8K, Thesios 927K); runs have
19.4-21K / 167K host reads. Result hashes of the FAISS runs match the no-hint run (`RESULT_SHA256`), i.e. the hints did not
change what the application computed.

FAISS, 20k queries, 1 GiB guest:

| policy | hit ratio | full hit | traffic |
|---|---|---|---|
| none | 30.2% | 15.5% | 1.00x |
| `learned` (no hints) | 74.3% | 72.8% | 1.66x |
| `learned` + hints, **no filter** | 95.6% | 89.8% | 4.97x |
| `learned` + hints + learned filter (theta 30), no residency annotation | 89.4% | 84.6% | 1.73x |
| `learned` + hints + **`mincore` residency annotation, no filter** | 95.5% | 89.3% | 4.97x |
| **`learned` + hints + `mincore` annotation + learned filter (theta 30)** | **95.5%** | **89.8%** | **1.74x** |

Thesios, 150k reads, 2 GiB guest, hint = the read K ahead:

| policy | hit ratio | full hit | traffic |
|---|---|---|---|
| none | 8.6% | 6.1% | 1.00x |
| `learned` (no hints) | 81.1% | 73.5% | 1.80x |
| `learned` + hint K=1 | 99.7% | 99.5% | 1.87x |
| `learned` + hint K=4 | 99.7% | 99.5% | 1.86x |
| `learned` + hint K=16 | 99.6% | 99.4% | 1.87x |
| `learned` + hint K=4 + learned filter | 99.7% | 99.4% | 1.86x |

* **FAISS: +21 points of hit ratio (74 -> 95.5%) at essentially `learned`'s traffic**, but only with both halves: the hint says
  *what* will be read, the `mincore` annotation says *which of it the guest already has*. Without the annotation the filter
  recovers 15 of the 21 points; without the filter the traffic is 5x.
* **Thesios: 99.5% of reads fully cached** (was 73.5%) for +4% traffic over `learned` (hint K=1..16 are equivalent; one read of
  lookahead is enough in this simulation because prefetches are instant). The filter has nothing to remove: every hinted
  read was needed (the guest rarely holds a Thesios range). The offline oracle (section 2, 95-98%) understated this because
  of the imperfect host-request-to-application-read alignment.
* This is the "hit rate with and without oracle information" answer: **without any hint ~74% (FAISS) / 81% (Thesios) hit
  ratio; with a realistic in-band hint 95.5% / 99.7%.** Everything here is gatherable with an application hook plus a
  `mincore` call, no kernel tracing.

## 10. Caveats of Part 2

* Prefetches are instant (nbd_server's simulated mode), so lead time is free; the delay study of section 7 shows how
  hit rate falls when hints are late. Guest timings in these runs are dominated by the hint round trips (FAISS query mean
  3.2 ms vs 2.2 ms without; 127 s vs 52 s per run) and say nothing about real latency: hints are synchronous O_DIRECT reads
  from the application's thread. A real shim would batch or send them asynchronously.
* The hint source is the application's own plan (FAISS's quantizer output, the trace's next reads): an upper-bound-quality
  hint. A coarser hint (only one list, only some reads) is covered by the degradation study, not re-run live.
* Single runs; FAISS 20k queries and Thesios 150k reads per cell. The `mincore` annotation changes nothing the
  application sees but its cost (one syscall per probed list) is not charged here.
* The learned filter's features were chosen from the part-1 sweep (popularity, residency, recency, size); it was not tuned
  per workload. Other `SIGNALS.md` rows (cgroup, ioprio, HW counters, guest rq flags) were not collected: the capture shows
  no signal in the host-visible ones, and the rest need privileges this machine lacks.
