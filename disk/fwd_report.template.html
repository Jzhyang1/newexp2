Remote Disk Readahead

A VM attached to a disk across a data-center network, with and without a local disk cache that reads ahead of it. This version puts a real guest in the loop, because the guest's own page cache and readahead change the answer.

This replaces an earlier version of the report, whose headline was wrong for real VMs. Corrections, each backed by data further down:
  • The first version replayed the guest's reads from a host process, one at a time. A real guest overlaps its reads and reads ahead on its own, which shrinks what a host cache can add. The replay's FAISS speedups of {{rep_f_z}}–{{rep_f_r}}× compare with {{sp_ra_z}}–{{sp_ra_r}}× for a VM.
  • The stream-readahead policy ignored its depth setting and fetched 16–32× more than plain readahead, so that comparison was unfair.
  • Timer slop in the emulated link inflated same-zone latencies: a same-zone 128 KiB read measured {{old_z}} µs in the first matrix and {{new_z}} µs after the fix.
  • The VM-trace workload is dropped: its source file was accidentally overwritten and only an approximation remains.
  • While sweeping readahead depth I found that the cache implementation held one lock while copying pages, which makes guest reads wait behind prefetch writes. I reduced it (the cache file is now memory-mapped) and re-measured every cached configuration with the final code; the lock itself remains and is quantified below.

The short version

  • A real guest already hides most of a data-center round trip. With the guest's own page cache, readahead and overlapped reads, FAISS queries over a same-zone or cross-zone link take {{d_z}} ms and {{d_a}} ms per query, against {{loc_z}} ms on a local disk. Direct remote access costs only {{gap_z}}× to {{gap_a}}× a local disk, so there is little penalty left to remove.
  • On top of that, host readahead does not help at data-center distances ({{sp_ra_z}}× same zone, {{sp_ra_a}}× cross zone) and moves {{amp_ra}}× the bytes over the link, because only {{used_ra}}% of the pages it prefetches are ever used.
  • It does help when latency is high or the guest is not reading ahead. At 60 ms it removes {{pen_ra_r}}% of the remote penalty ({{sp_ra_r}}×). With the guest's readahead turned off it removes {{abl_pen0}}% of the penalty ({{abl_sp0}}×).
  • Serving one read at a time hurts more than not caching. The same guest is {{c1_ratio_z}}× to {{c1_ratio_r}}× slower (same zone to cross region) when nbd_server handles one request at a time, because {{queued_pct}}% of the guest's reads arrive with another already queued.
  • Caching without prefetching is slightly slower than direct at data-center distances ({{sp_ca_z}}× same zone, {{sp_ca_a}}× cross zone) and slightly helpful at 60 ms ({{sp_ca_r}}×). The stream-detecting and QuickMine policies did not beat plain readahead anywhere that readahead helps.
  • Reading further ahead makes it worse. Sweeping the host's readahead from 64 KiB to 32 MiB, the best depth is {{best_d_region}} pages (1 MiB) at 60 ms and 1–4 pages (64–256 KiB) at the data-center links; every link slows down beyond that, and at data-center speeds a 4 MiB window is already a slowdown ({{sp_d64_zone}}× and {{sp_d64_az}}× direct speed).

What was measured

Two kinds of experiment, which disagree for the reasons this report explains. In both, the remote disk is a separate process on this host whose round-trip time and bandwidth are enforced with real waits. The headline metric for the VM runs is the guest's mean FAISS query latency, measured by the guest itself.

Data-center latencies used

Round-trip time within a zone is about a third to half a millisecond, crossing zones in the same region costs roughly 0.4 to 2 ms, and a US coast-to-coast hop is tens of milliseconds.

How accurate is the emulated link?

Measured by reading through the emulator with no cache and no guest. The gap to the arithmetic model is software cost (loopback TCP, thread handoffs, copies): about {{cal_0}} µs for 4 KiB and {{cal_0b}} µs for 128 KiB even with every delay set to zero. At 60 ms the error is under 1%.

Why a real guest changes the answer

1. The guest reads ahead itself, and the effect depends on how much

I changed the guest kernel's read_ahead_kb for the data disk and repeated direct versus host-readahead at the cross-zone link, two runs each. With none, every 4 KiB page fault becomes its own round trip ({{abl_reads0}} NBD reads per query instead of {{abl_reads128}} at the default), and host readahead rescues it. With a larger guest window the guest already over-reads by itself ({{abl_mb1k}} MB crossed the link against {{abl_mb128}} MB at the default), and adding host readahead on top only adds waste.

{{LEG_ABL}}

2. The guest overlaps its reads

QEMU's NBD client sends requests without waiting for replies: in a captured FAISS run, {{queued_pct}}% of reads arrived at the server with another request already in the socket. My first nbd_server handled one request at a time per connection, so those reads queued behind each other and each paid a full round trip. I added a read_concurrency option, now the default (8), that serves reads in parallel and may reply out of order, as NBD allows; read_concurrency: 1 reproduces the old behavior. A test sends 24 pipelined reads and checks every payload. Every VM number above, other than the "serial server" bars, uses overlapped reads. The local-disk references were re-measured after the default changed.

Serving one read at a time makes direct access {{c1_ratio_z}}× slower per query at the same-zone link, {{c1_ratio_a}}× cross-zone and {{c1_ratio_r}}× at 60 ms. It hurts the cached configuration too, by {{ra_c1_ratio_r}}× at 60 ms, because cache misses queue as well.

{{SERIAL}}

3. Why the replay overstated the benefit

The replay reads one block at a time, which is what the serial server does, so the like-for-like comparison is the VM with the serial server both with and without readahead. That comparison gives {{vm1_z}}×, {{vm1_a}}× and {{vm1_r}}× at the three links, against the replay's {{rep_f_z}}×, {{rep_f_a}}× and {{rep_f_r}}×: within {{rep_over_vm1_r}}% at 60 ms, but the replay is {{rep_over_vm1_z}}% and {{rep_over_vm1_a}}% higher at the data-center links, for a reason I did not find (the replay has no guest page cache or readahead, which may be part of it). The speedup a real guest actually sees is the overlapped-versus-overlapped one.

{{LEG_CMP}}

Two checks support this reading at 60 ms. First, the replay's direct run waited {{win_d}} s in total over the first 6,700 reads of the trace, and the VM with the serial server spent {{vm_c1_d_sum}} s in queries (its 2,500 queries produce about that many reads). Second, with readahead the replay took {{win_r}} s ({{win_sp}}×), the VM with the serial server {{vm_c1_r_sum}} s, and the VM with overlapped reads {{vm_c8_r_sum}} s. The speedup is the same for the first 6,700 reads of the trace ({{win_sp}}×) as for the window the main replay used, so the choice of trace window does not explain the gap.

How far ahead should the host read?

After every guest read, the host's readahead policy fetches a fixed number of cache pages starting at the end of that read. The main runs use 16 pages of 64 KiB, which is 1 MiB, eight times the guest's own 128 KiB window. I swept it from 1 page (64 KiB) to 512 pages (32 MiB, the policy's limit), in the VM at all three links, with the guest's readahead at its default.

What I expected. To hide one round trip, the host has to be ahead of the guest by about (rate the guest consumes) × (round-trip time). At the guest's local-disk speed that is about {{need_zone}} MiB at the same-zone link, {{need_az}} MiB cross-zone and {{need_region}} MiB at 60 ms. So 1 MiB should be plenty at data-center distances and about {{used16_region_need}}% of what 60 ms needs, and deeper should help there.

What happened. It did not help, at any link. Each chart shows the median guest query latency against depth, with direct access and the local disk as reference lines.

{{DEPTH}}
  • The best depth is {{best_d_zone}} page(s) at the same-zone link ({{best_sp_zone}}× direct), {{best_d_az}} cross-zone ({{best_sp_az}}×) and {{best_d_region}} pages, 1 MiB, at 60 ms ({{best_sp_region}}×). At data-center distances those gains are small enough to be within noise.
  • Beyond that, every link gets slower. At 4 MiB (64 pages) the guest runs at {{sp_d64_zone}}× and {{sp_d64_az}}× of direct speed at the data-center links, slower than direct, and {{sp_d64_region}}× at 60 ms. At 16 MiB: {{sp_d256_zone}}×, {{sp_d256_az}}× and {{sp_d256_region}}×.

Why reading further ahead loses

Three effects, each measured. The table below the list has every diagnostic run.

  • Most of what it fetches is never used. At 1 MiB, {{used16_az}}% of prefetched pages are read by the guest (cross-zone); at 16 MiB only {{used256_az}}%, and {{wasted256_az}}% are evicted unused. Traffic over the link grows from {{amp16_az}}× to {{amp256_az}}× the bytes direct access needs. FAISS jumps between inverted lists, so only the pages right after a read are likely to be wanted. The scan model behind my estimate does not describe this workload.
  • It pushes out pages the guest needs, which is what costs the most at 60 ms. The share of pages that still miss rises from {{miss16_region}}% at 1 MiB to {{miss256_region}}% at 16 MiB, and the fraction served from cache falls from {{hit16_region}}% to {{hit256_region}}%. With a cache four times larger, depth 256 recovers from {{dg_base_region}}× to {{dg_big_region}}× at 60 ms, so the cache was too small for that depth. Even then, depth 16 with the larger cache does better still ({{dg_d16big_region}}×): more depth was never better, only less bad.
  • At data-center speeds the host becomes the bottleneck. A larger cache helps little cross-zone ({{dg_base_az}}× to {{dg_big_az}}×) and removing the bandwidth limit makes it worse ({{dg_nobw_az}}×), so neither the cache size nor the link explains it. What does grow is contention on the cache's one lock: guest reads waited {{lw16}} µs each at depth 16 and {{lw256}} µs at depth 256, while the prefetchers held that lock for {{hold256}}% of the run (against {{hold16}}%). Cross-zone, that wait alone is about {{lwq256}} ms of the {{q256_az}} ms per query at depth 256 (against {{q16_az}} ms at depth 16).
The lock is an implementation cost, not a property of readahead. The cache copies each fetched page into its local store while holding one lock. Switching the store from pwrite to a memory-mapped file cut guest-read lock wait at depth 256 from {{lw256_old}} to {{lw256}} µs per read and the prefetchers' hold from {{hold256_old}}% to {{hold256}}% of the run, but the copy still happens under the lock. A design that copied pages outside the lock would probably do better at depth. By how much, I did not measure.

Odd details I checked

The emulator's timer slop was inflating same-zone numbers

A plain sleep overshoots by about {{ovr_us}} µs on this kernel, and each emulated read waits two to four times. A same-zone 128 KiB read measured {{old_z}} µs in the first matrix against a model of {{cal_z128m}} µs. The emulator now sleeps to within 100 µs of each deadline and spins the rest: the same read measures {{new_z}} µs in the rerun ({{cal_z128}} µs in the calibration above).

The stream policy was 16–32× more aggressive than plain readahead

It prefetched a fixed 512 pages regardless of the configured depth. On the FAISS replay cross-zone it moved {{stream_amp_old}}× the bytes read and ran at {{stream_sp_old}}× direct speed; at the same depth as plain readahead it moves {{stream_amp_new}}× and runs at {{stream_sp_new}}×. The policy now honors readahead_pages.

Caching without prefetch is slightly slower than direct on sequential reads

Every miss pays to store the data locally: {{cache_extra}} µs more per 128 KiB read at the same-zone link. In isolation a 128 KiB pwrite to the cache file took {{pwrite}} µs (the cache now stores pages with a memcpy into a memory-mapped file), and the cache directory here is tmpfs, so a real SSD cache would add more unless writes were made asynchronous, which I did not try.

QuickMine does nothing on one-pass workloads

It predicts a page only after seeing the same transition twice. The synthetic workloads never repeat one, and the most pages it ever prefetched on them is {{qm_synth_max}}. On the FAISS replay it fires ({{qm_f_iss}} pages issued, {{qm_f_used}} used), and in the VM it issued {{qm_vm_iss}} pages with {{qm_vm_used}} used, which is {{qm_vm_sp}}× direct speed.

Random reads get hits by chance

Readahead on random 4 KiB reads shows {{rnd_hit}}% of reads with no wait. That is not prediction: the 256 MiB cache holds {{cover}}% of the 1 GiB test disk, so a random page is often already resident. A larger disk would make this vanish.

The concurrent default has a cost on fast local disks

nbd_server starts a thread per read when read_concurrency is above 1. With the guest's readahead off (38 reads per query) a local-disk run took {{loc0_serial}} ms per query under the old serial server and {{loc0_conc}} ms with the concurrent default; at the guest's default readahead the difference disappears ({{locd_serial}} vs {{locd_conc}} ms). That is negligible against the 0.4 ms and larger latencies studied here, and every remote number carries the same cost, but a worker pool would remove it for local-disk use.

The VM-trace workload is gone

While testing, I truncated logs/nbd_access.csv (the original 193,799-row VM trace). I excluded the workload that depended on a reconstruction rather than present numbers from approximate data.

Data integrity through the VM

The guest hashes every search result. All {{integ_n}} configurations (local disk, direct, serial server, cache only, readahead, stream, QuickMine) produced {{integ_distinct}} distinct hash, so each path returned exactly the same neighbors. The replay verifies every byte read against the disk image; mismatches across all {{n_replay}} runs: {{mism}}.

Limits of these results

  • One VM workload. Only FAISS ran inside a guest. YCSB and GUPS images exist but were not run, and a workload with large sequential scans through a guest (where host readahead might fare better) was not tried.
  • One guest at a time, 1 GiB RAM, one 256 MiB host cache. A larger guest page cache would hide more; several guests sharing a link would raise the price of wasted prefetch traffic.
  • Baselines drift between sessions. Re-measuring the direct baselines at the end of the session gave results up to {{drift_max}}% different from the first measurement (table below). Differences smaller than about 10% at the data-center links are therefore not resolved by these runs. The direct baselines in this report use both sets of runs.
  • Cross-region VM runs use 2,500 queries (5,000 elsewhere), with 2 repetitions, because they are slow. Comparisons are made within a link, never across links. The local-disk reference uses the same query count.
  • The network is emulated on one host over loopback: no packet loss, no competing traffic, no queueing at the remote disk beyond the shared link. Same-zone numbers carry the most relative error from software cost (see the calibration table).
  • Readahead sizes were not tuned (1 MiB for the VM and FAISS replay, 512 KiB for synthetic workloads), nor was QEMU's NBD client configured beyond defaults.
  • The remote disk is read-only; guest writes go to a local overlay, and no write-heavy workload was tested.
  • The replay's benefit over a serial baseline is real for any server that handles reads one at a time, but this report does not claim any production NBD server does.
